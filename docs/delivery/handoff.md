# 接手与交接手册

## 第一次进入仓库

1. 阅读 README → AGENTS → STATUS → roadmap，确认目前只有文档还是已有可运行工程。
2. 检查 git 状态与分支；读取最新 PR/Issue。不要覆盖未提交修改，不假设前一 Agent 的口头总结等于代码事实。
3. 运行 `python3 scripts/check_docs.py`，记录结果；检查任务依赖、功能与测试编号。
4. 默认从 T01 的 M0 验证任务开始。先做原生玻璃/键盘/滚动技术样例，再逐阶段扩大，不绕过视觉可行性直接堆业务。
5. 若已有实现，先跑当前工程真实检查并对照功能目录；不要为了符合新架构文档无理由推翻已验证代码。

## v3.1 文档评审补充

新 Agent 可参考 [v3.1 产品演进取舍](../product/v3.1-evolution-review.md) 与 [首个 APK 垂直切片](first-apk-vertical-slice.md)，优先验证 T01/T02/T03/T04/T07/T08 的本地记录闭环。当前只有设计提案；四个主入口、已有任务依赖、F01–F20 完整范围不变。边缘 AI 与概念对撞暂不属于首版 APK。

## 下一位 Agent 的明确第一单

T01–T04：冻结兼容工具链，建立 Android 可运行工程和合成测试数据；实现四入口框架、GlassSurface 原型、快速输入与系统键盘联动，采集 60/120Hz 设备证据。产出可安装内测样例、视觉录屏、依赖矩阵、性能报告及 ADR 更新。没有真机时先完成可编译样例与模拟器交互，真机项标 blocked，不能宣布流畅度通过。

同步进行的纯文档/接口细化可以继续。需要并行 Agent 时先遵守会话授权；一名集成人负责 schema、设计 token 和契约，其他人按文件边界工作。

## 交接模板

```text
任务 ID / 功能 ID：
当前分支 / commit / PR：
已完成的用户可见结果：
改动文件与重要决策：
执行的验证命令、设备、结果：
未执行的验证及原因：
数据迁移/权限/费用影响：
已知问题与可复现步骤：
下一任务与依赖：
工作区未提交改动：
```

交接放 `docs/handoffs/YYYY-MM-DD-task.md`，并更新 STATUS。证据文件使用合成资料；视频大文件放受控 release/构建附件，记录稳定链接和 SHA，不塞入 git 历史。失败记录也保留，防止后续反复踩坑。

## 功能状态如何推进

planned → in_progress：任务认领且有分支。in_progress → implemented：正常/失败路径已实现并有相关自动测试。implemented → verified：质量门槛和关联验收全部有证据。任何状态可 blocked，但要写阻断原因和解除条件；不能把 blocked 改成“已完成但后续完善”。

feature-catalog 的 evidence 数组写入报告路径或 PR URL。当前为空是有意的：本次只建立设计与协作基线。下一位 Agent 不应删除这项诚实边界。
